# Project Architecture Overview

## Product

Athlete Social Network (“The Athlete Passport”): a LinkedIn-style network for athletes built around public sporting identity, verified achievements, club affiliation, and trainer-reported sport metrics, with athlete-controlled visibility. Medical records and OCR are no longer part of the product ([ADR-013](adr/013-pivot-clubs-metrics-trainer-portal-and-visibility.md)).

## Regulatory posture

- Colombian Habeas Data (Ley 1581 de 2012)
- Future-ready for GDPR-style controls

## Core principle

The architecture is intentionally rigid because most code will be generated by AI agents.

## Applications

- `apps/api` — Fastify + tRPC v11 backend
- `apps/web` — Next.js App Router public web / SEO
- `apps/mobile` — Expo + React Native with expo-router
- trainer portal — planned; surface (web or mobile) not yet decided

## Shared packages

- `packages/validators` — Zod schemas and inferred types
- `packages/auth` — Supabase auth wrapper and hooks
- `packages/crypto` — `encryptPII()` and `decryptPII()` only (JSON helpers are internal)
- `packages/api-client` — typed tRPC client + hooks
- `packages/shared-logic` — pure TS utilities, constants, converters, formatters
- `packages/queue` — BullMQ queue definitions and job payload types

## Monorepo principles

- apps are isolated from each other
- packages are imported by apps, not vice versa
- UI is app-specific
- contracts are schema-first
- visibility is enforced on every endpoint that returns athlete data, list and detail alike
- RLS is tested and treated as a first-class security boundary

## Operational spine

Zod → tRPC → Prisma

## Data flows

### Public athlete profile

Next.js Server Component → tRPC `createCallerFactory` → explicit Prisma `select` → visibility filter → public-safe output schema

### Profile photo

Mobile upload request → `storageRouter` signed upload flow → storage confirmation → BullMQ `optimizeImage` job (EXIF stripped) → public 150/400/1200 WebP variants

### Trainer-reported metric entry (planned)

Trainer request → membership check (`ACTIVE` `ClubMembership` for the trainer's club) → entry persisted with reporting trainer → `AthleteMetricSummary` derived → visible to others only as the athlete's visibility settings allow

## Current state vs. target (known drift)

The pivot is not yet implemented. As of this writing:

- `prisma/schema.prisma` still contains `MedicalDocument` and `OcrJob`, and none of the pivot entities
- `apps/api` still mounts the `medical` router (alongside `athlete`, `achievement`, `connection`, `storage`, `sport`) and has the `processOCR` job
- `supabase/policies/` and `tests/rls/` still cover `medical_documents` and `ocr_jobs`
- `apps/mobile` still has a `documents` tab

These are pending removal and must not be extended.
