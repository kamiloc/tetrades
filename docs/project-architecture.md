# Project Architecture Overview

## Product

Athlete Social Network (“The Athlete Passport”): a LinkedIn-style network for athletes built around public sporting identity, verified achievements, club affiliation, and trainer-reported sport metrics, with athlete-controlled visibility. Medical records and OCR are no longer part of the product ([ADR-013](adr/013-pivot-clubs-metrics-trainer-portal-and-visibility.md)).

## Regulatory posture

- Colombian Habeas Data (Ley 1581 de 2012)
- Future-ready for GDPR-style controls

## Core principle

The architecture is intentionally rigid because most code will be generated by AI agents.

## Applications

- `apps/api` — Fastify + tRPC v11 backend
- `apps/web` — Next.js App Router public web / SEO
- `apps/mobile` — Expo + React Native with expo-router
- trainer and admin portals — web (`apps/web`), built in `add-web-portal-shell` and `add-trainer-portal`; the backend for both ships in `add-admin-club-trainer-management` ([ADR-017](adr/017-platform-admin-trainer-provisioning-and-club-lifecycle.md)). Mobile onboarding tells trainer accounts to use the web portal.

## Shared packages

- `packages/validators` — Zod schemas and inferred types
- `packages/auth` — Supabase auth wrapper and hooks
- `packages/crypto` — `encryptPII()` and `decryptPII()` only (JSON helpers are internal)
- `packages/api-client` — typed tRPC client + hooks
- `packages/shared-logic` — pure TS utilities, constants, converters, formatters
- `packages/queue` — BullMQ queue definitions and job payload types

## Monorepo principles

- apps are isolated from each other
- packages are imported by apps, not vice versa
- UI is app-specific
- contracts are schema-first
- visibility is enforced on every endpoint that returns athlete data, list and detail alike
- RLS is tested and treated as a first-class security boundary

## Operational spine

Zod → tRPC → Prisma

## Data flows

### Public athlete profile

Next.js Server Component → tRPC `createCallerFactory` → explicit Prisma `select` → visibility filter → public-safe output schema

### Profile photo

`storage.getUploadUrl` (server-built path in the private `profile-photo-originals` bucket) → client uploads directly to Supabase Storage → `storage.confirmUpload` (15-minute window, object exists) → ORIGINAL row `QUEUED` → BullMQ `optimizeImage` job (EXIF stripped) → 150/400/1200 WebP variants in the public `profile-photos` bucket → rows `READY`, avatar set to CARD_400 ([ADR-015](adr/015-profile-photo-storage-split-buckets-and-upload-window.md))

### Trainer-reported metric entry

`metric.reportEntry` (`trainerProcedure`: `ClubTrainer` row for the club) → transaction: `ACTIVE` `ClubMembership` check → entry persisted with reporting trainer and authorizing membership → `AthleteMetricSummary` derived (latest value, count, and personal best per the definition's `direction`) → visible to others only as the athlete's visibility settings allow (`services/visibility.ts`, list and detail alike)

### Trainer certification of an achievement

`achievement.requestCertification` (athlete; club with an `ACTIVE` membership) → transaction: `PENDING` request persisted, achievement `PENDING` → BullMQ `notifications` jobs to the club's trainers (`CERTIFICATION_REQUESTED`, ids only) → `achievement.decideCertification` (`trainerProcedure`; `ACTIVE` membership re-checked) → request `APPROVED` / `REJECTED` (with reason) and achievement `VERIFIED` / `REJECTED` in one transaction → athlete notified (`CERTIFICATION_DECIDED`) → public reads show the certifying club only when the club-memberships audience allows ([ADR-016](adr/016-achievement-certification-by-club-trainers.md))

### Platform admin: clubs and trainer provisioning

Admin account (role `ADMIN`, set by the owner with SQL) → `admin.*` (`adminProcedure` re-reads the role every call) → `createClub` / `updateClub` (slug immutable) → `inviteTrainer` (email lowercased, `PENDING` for 14 days, no email sent) → invitee signs in with that address → `trainerInvitation.listMine` / `accept` (session email must be confirmed; athlete and admin accounts rejected) → `ClubTrainer` row created or restored → `admin.revokeTrainer` sets `revokedAt` (row kept). Every admin write appends to `admin_action_log` in the same transaction ([ADR-017](adr/017-platform-admin-trainer-provisioning-and-club-lifecycle.md)).

### Club deactivation

`admin.deactivateClub` → transaction: club locked `FOR UPDATE`, `deactivatedAt` set → `PENDING_ATHLETE_CONFIRMATION` memberships `REJECTED` → `PENDING` certification requests `CANCELLED`, achievements `UNVERIFIED` → `PENDING` trainer invitations `REVOKED` → admin action logged → after commit, BullMQ `notifications` jobs (`CLUB_INVITATION_CLOSED`, ids only, naming no club). `ACTIVE` memberships, entries, verified achievements and trainer rows are unchanged; every club output reports `isActive: false`. Trainer writes lock club → club_trainer → membership → achievement → request, so in-flight writes either commit first or fail. `admin.reactivateClub` restores access; closed items stay closed.

### Scheduled jobs

`trainer-invitation-redaction` is the first recurring job: registered at API startup with BullMQ's `upsertJobScheduler` (idempotent across restarts and instances), daily, payload `{ requestId }` only. The worker selects its own rows and logs counts with the run's `requestId`. Later recurring jobs (the tombstone purge) follow the same pattern: a fixed scheduler id, a payload of ids or nothing, a worker in `apps/api/src/jobs/`, and re-runnable, set-based work.

### Club invitation

`club.inviteAthlete` → `PENDING_ATHLETE_CONFIRMATION` membership persisted → BullMQ `notifications` job (`CLUB_INVITATION`, ids only) → push via Expo HTTP API → athlete accepts or rejects through `club.respondToInvitation`

### Data deletion (Habeas Data)

`athlete.requestDeletion` → `DataLifecycleRequest` persisted → BullMQ `pii-deletion` job → legal-hold check → read the confirmed email → cascade delete (trainer invitations to that email revoked and redacted, ADR-017), Storage and auth-user removal → tombstone athlete and account (retained audit and consent rows) → verification → `COMPLETED` or `FAILED`

## Current state vs. target (known drift)

The medical/OCR removal (`remove-medical-ocr-domain`) is applied in code, schema, policies, tests, and the database (migration `20261004003536_remove_medical_ocr`). The `medical-documents` Storage bucket is deleted (verified 2026-10-06). Profile photos now use two buckets, `profile-photos` (public) and `profile-photo-originals` (private), per ADR-015. The club, metric, trainer, and visibility model (ADR-013, `add-clubs-metrics-visibility-model`) is implemented in schema, RLS, services, and the `club`, `metric`, `visibility`, and `notification` routers, and the `deletePII` and `sendNotification` workers are real. Remaining drift:

- the trainer and admin web portals do not exist yet (backend ready, ADR-017); athlete UI screens for metrics and visibility are partial
- trainer-only accounts can't request deletion in the app; the owner handles them manually (ADR-017 known gap)
- mobile push-token registration (`expo-notifications`) is not wired
- no scheduled job yet purges deletion tombstones after the 5-year audit and consent retention
- there is no data-export endpoint
